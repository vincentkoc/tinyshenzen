# tinyworlds

Miniature, explorable pixel-art cities. Each **world** is one city redrawn as an isometric
pixel-art map, generated procedurally from open data and served as a pannable, zoomable tile
map under its own path:

| World     | City                                 | Notes                                                        |
| --------- | ------------------------------------ | ------------------------------------------------------------ |
| `tinynyc` | New York City, the five boroughs     | surveyed building heights, street-tree census, ferries       |
| `tinyrao` | Ribeirão Preto, São Paulo, Brazil    | heights estimated from a satellite raster, cane fields around |
| `tinyorl` | Orlando, Florida (the built-up area) | downtown, the lakes, the airport and theme-park country      |
| `tinyfte` | El Calafate, Patagonia, Argentina    | the town on Lago Argentino and the steppe; heights from the raster |
| `tinyvlc` | Valencia, Spain                      | old town, Turia gardens, City of Arts and Sciences, port and beaches |
| `tinylas` | Las Vegas, Nevada                    | the Strip, downtown, the airport and the desert valley       |
| `tinylax` | Los Angeles, California (the basin)  | downtown, Hollywood and its sign, the beaches, the stadiums, LAX; County community lines |
| `tinydal` | Dallas, Texas                        | downtown and Reunion Tower, the Arts District, Fair Park, the Trinity and its arch, Love Field; lit buildings and the quiz |
| `tinycvg` | Cincinnati, Ohio (and Covington, Newport) | downtown, Over-the-Rhine, the Roebling Bridge and the Ohio, Union Terminal; lit buildings and the quiz |
| `tinypit` | Pittsburgh, Pennsylvania             | the Golden Triangle and the Point, the three rivers and their bridges, the North Shore, the inclines, Oakland; lit buildings and the quiz |
| `tinyphl` | Philadelphia, Pennsylvania           | Center City and City Hall, Independence Hall, the Parkway and the Art Museum, University City, South Philadelphia's rowhouses; lit buildings and the quiz |
| `tinycos` | Colorado Springs, Colorado            | downtown and Colorado College, Old Colorado City and Manitou Springs, the Garden of the Gods' red rocks, the Broadmoor, the Air Force Academy and its chapel; lit buildings and the quiz |
| `tinytkf` | Truckee, California                  | Commercial Row and the depot, the Truckee River, Donner Lake and the Pioneer Monument, Tahoe Donner, the airport; lit buildings, no quiz (too few on Wikipedia) |
| `tinywinterfell`, `tinykingslanding` | imagined places | no map data: generated by code from scratch (fan-made, unofficial) |
| `tinywesteros` | an imagined world | Westeros and Essos as one toy-scale diorama, north up, with a clean rectangular frame |

A front page lists the worlds, the cities people are funding next, and links the source. Its
footer, like every page's, links the terms of service and the privacy policy (`/terms/`,
`/privacy/`, in the three languages): the privacy policy says what the site and the API
collect, so it changes with them (`tinyworlds-frontend/CLAUDE.md`).

## This repository is public

Nothing about where or how the site is deployed belongs in a tracked file: no domain, host, IP,
server path, hosting-panel ids, analytics host or site id, payment links, and of course no keys.
All of that lives in the gitignored `deploy/.env` (template: `deploy/.env.example`) and in the
hosting panel's own env vars. Docs and examples use `example.com`. Check `git diff --cached` for
such strings before every commit.

## Layout

```
tinyworlds/
├── tinyworlds-pipeline/   # TypeScript ESM CLI: open data → isometric pixel-art tiles + indexes
├── tinyworlds-frontend/   # Next.js 16 static export: the map viewer (one build per world), the front page, `/admin/` and `/me/`
├── tinyworlds-api/        # NestJS + GraphQL + Prisma: donations, per-city funding milestones, the donation funnel (admins), benefactors, their links and donors' own page (`/me/`), and the mails (sign-in, thank-you, a city is built)
├── tinyworlds-videos/     # HyperFrames: the front page's card loops and hero, city flyovers, the showcase film, a tour of tinywesteros
├── deploy/                # nginx config, deploy script, .env.example
├── dev.sh                 # tmux launcher
└── CLAUDE.md / README.md
```

Each sub-project has its own `CLAUDE.md`.

## How the pieces fit

- **The maps are static.** Tiles and JSON indexes are generated offline by the pipeline and
  served as files; the viewer needs nothing else to show a city.
- **The API exists for donations** (and keeps the answers of "Guess the building", below). Each proposed city is built when donations for it reach
  its goal (US$30); what comes in above the goal pays for servers and upkeep, and the most
  funded cities are built first. The Donate dialog and the front page read `cityMilestones` (the
  ranking) and start a Stripe Checkout through `createDonationCheckout` for the city and amount
  the donor chose; a Stripe webhook records what was paid. If
  the API is unreachable the viewer falls back to static payment links, so donating never
  depends on it.
- **Guess the building** (New York, Dallas, Cincinnati, Pittsburgh, Philadelphia, Colorado Springs): a lit building, its Wikipedia opening with the name
  blanked, four names to pick from (`quiz.<locale>.json`, made by the pipeline). Each answer
  goes to `answerQuiz`, once per visit and building, which answers how everyone has answered
  that building; without the API the game plays on without the shares.
- **The funnel is the site's own.** Every page says to the API that a visit opened it, and
  then which steps towards a donation that visit took (the donate sign, the checkout, giving
  up); a visit is a tab's stay, named by an id made up in the browser and kept nowhere else
  (no cookie, no address). That gives the donation funnel and each city's count of visits,
  which admins read at `/admin/` (part of the front page's build). Admins sign in through a
  link sent by email; who they are is the API's `ADMIN_EMAILS`, never a tracked file.
- **Every card says how visited its world is.** The front page's cards show each world's visits
  since the site opened (the page analytics' history up to 2026-11-10, the site's own count
  after) and, above ten, how many have that map open now; each group of cards comes most
  visited first. An open map tells the API every half minute while it is in view
  (`trackPresence`), which keeps its visit's `last_seen_at` fresh: a visit keeps when it started
  and when it was last seen, for whatever the data is wanted for later.
- **Donors and benefactors.** A donor is an email address: the one Stripe took at checkout, or
  any address that signs in. No password, no account made by hand. Anyone may sign in (a link
  or a 6-digit code sent by email, `purpose: "donor"`) and read their own page, "Your cities" at `/me/` of the front page's build:
  what they gave, the badges they earned (founding number, first stone, keystone) and whether
  they are named. Each city's public benefactors (`cityBenefactors`: founders, then benefactors
  by amount, one stone per US$1) are shown on a sign from the front page and from About in a map; a built
  city, which the Donate sign does not offer, reaches Donate only through that sign. Names are the donor's choice, per city; admins can hide one on `/admin/`. Emails never
  appear in the API's answers, and no answer says whether an address has donated.
- **Benefactors' links, and everyone on the front page.** A donor who has given may add up to
  three links to their own pages on "Your cities". The API reads each page once, when it is
  saved (title, description, picture, icon), and keeps small copies of the pictures, so a
  visitor's browser never asks a linked site for anything. The links show wherever the donor's
  name does, never beside an unnamed gift; their pictures show once the donor has given US$10
  in all. Admins see every link on `/admin/` and can hide a donor's links (hiding the name
  hides them too). The front page lists **everyone who gave to a city** (`benefactorWall`),
  under "Our Benefactors": down both sides of the page where the screen has room, as a strip
  under the figures where it has not; a named donor once, with what they are named for and
  their links, every unnamed gift as "Anonymous" with what it gave and where.
- **Cities brought by their benefactors are praised.** A city that is on the map because its
  gifts met its goal (built, with `raisedCents` at least `goalCents`; one built by hand before
  anyone gave is not) carries a gold plaque: "Brought to you by 2 benefactors, who donated
  $35", how many people gave to it (`benefactorCount`: a donor once, however many gifts) and
  what they gave. It is on its card on the front page (with a gold bar along the card's top,
  leading to its hall of fame), in the hall's gallery and on the city's own hall.
- **The hall of fame** (`/hall-of-fame/`, part of the front page's build): what everyone gave
  in three figures, the cities their benefactors brought to the map (each with its picture and
  plaque), everyone who gave, ranked, with their links, then the other cities; each city leads
  to **a hall of its own** (`/hall-of-fame/<city's slug>/`): its picture, its foundation, its
  founders and its benefactors as cards.
  Unlike `/me/` and `/admin/` these pages are for search engines too. **The links say
  `dofollow`**, never `nofollow` or `sponsored`, and the benefactors are told so, which is why the
  pages are **baked** with what the API says when the front page is built (the names and the
  links are in the HTML itself) and ask the API again once open. The daily deploy run builds
  the front page again, so what is baked is at most a day old. A city named since the build
  has no page yet: the web server sends its address to `/hall-of-fame/?city=<slug>`, which
  shows it all the same.
- **Lists: anyone may ask to hear.** On a city being funded, "Tell me" puts an address on its
  list; "Tell me when new cities are built" puts it on the list of every new world. Signing in
  (a link or a code, `purpose: "donor"`) confirms the address, and the join rides on the link,
  server side. A welcome mail follows, with three lit buildings from the cities already on the
  map; one more mail goes out when the city is built (for "new cities", whenever a world is
  added), and nothing else is sent through the lists. A city's list ends with its mail, "new
  cities" lasts until the person leaves. Every list mail has a "Leave this list" link that
  needs no sign-in (`/lists/leave/#t=<token>`, `leaveListWithToken`) and the mail client's own
  unsubscribe (RFC 8058); lists are also left on "Your cities". A donor of a city is told
  without a list. The cards say "N waiting" (`waiting`); admins see counts only, on `/admin/`,
  never an address. The privacy policy covers all of it.
- **Donors get two mails, and two more, once each.** Every donor in a city's hall of fame is
  told so by a mail sent by hand, once each (`npm run hall:announce -- --send` in the API's
  container; without `--send` it only says who would be told): which halls they are in and
  how they show there, and that they may put links beside their name. The same donors get
  **the owner's own note**, once each and by hand the same way (`npm run owner:note --
  --send`; run again, it reaches those who have given since): a thank-you from the owner, not
  from the site, with the owner's WhatsApp for whatever a donor wants to say. Who the owner is
  (name, sender address, number) is the API's environment, never a tracked file. Otherwise (the lists' mails are above):
  once Stripe confirms a gift, the API thanks the donor by mail
  (how much closer their city is, its stones with theirs lit, how many people explore the
  cities, where they are listed); and once a city is built, `deploy/deploy.sh <world>` runs the
  API's announce command, which tells each of its donors, once, that it is on the map. The
  sign-in mail has the same look: the site's band and pixel wordmark, a white card on paper.
  The mails' pictures (wordmark, badges) are the front page's own files
  (`tinyworlds-frontend/public/email/`), the city's picture its real share card; `SITE_URL` is
  where they are. A mail never holds up or undoes a donation, a deploy or a sign-in, and goes
  only to the person's own address (`tinyworlds-api/CLAUDE.md`, Mails).
- **The front page moves.** Its hero goes round every world, one slide each, and each world's
  card plays a short silent loop; all are made by `tinyworlds-videos` from the world's own
  tiles and play over a still. They are the front page's own files, so nothing but its build
  needs deploying for them.
- **Google's tags wait for consent.** Google Tag Manager (and the Google Analytics in it) is the
  one thing on the site that sets cookies: visitors in Europe are asked first, and nothing from
  Google loads before they say yes (`tinyworlds-frontend/CLAUDE.md`, Analytics).
- **The interface follows the visitor's language** (en-US, pt-BR, es-ES), whatever the city.
  City data (street and place names) stays in the city's own language.

### Deviations from the global stack (deliberate)

- **The pipeline is a CLI, not a BullMQ worker.** It follows the worker conventions that apply
  (TypeScript ESM, Commander.js entry point, swappable data-source providers) but has no queue.
- **The frontend is a static export** (`output: "export"`), one build per world under
  `/<world>` plus one for the front page. No server components fetch at request time; Apollo
  Client is used only where the API is (the Donate dialog, the front page's milestones).
- **No accounts for visitors.** What the site calls for them is public and throttled. Auth
  exists for admins and for donors (who sign in to see the cities they helped build, or to
  confirm an address for a waiting list: still no account to make), and
  without passwords: a sign-in link or its code by email, then a JWT in local storage
  (`tinyworlds-api/CLAUDE.md`). Signing in is REST, as the global stack has it.
- **Funnel steps go out with plain `fetch`**, not Apollo Client: every page sends one, and
  Apollo is only downloaded when the donate sign or the admin page asks for it.
- **A link's pictures are served by REST** (`GET /api/link-images/<id>`): a page shows them
  with `<img>`, and they are kept in the database, not in a bucket (a few kilobytes each,
  drawn again by the API as WebP; there is no S3 in this project).

## Adding a world

1. Pipeline: `tinyworlds-pipeline/src/cities/<id>.ts` (see that project's `CLAUDE.md`), then
   `npm run all -- --city <id>` and `npm run cli -- --city <id> card`.
2. Viewer: `tinyworlds-frontend/src/worlds/<id>.ts` and its registry entry.
3. API: mark the city `BUILT` with its `worldId` (a line in `seed-data.ts`; the seed runs
   whenever the API starts; see `tinyworlds-api/CLAUDE.md`).
4. Videos: `npm run plates -- <id> && npm run loops -- <id>` in `tinyworlds-videos` gives the world its
   card loop on the front page (`tinyworlds-frontend/public/loops/<id>.mp4`); without one its
   card simply stays still. A framing in `HEROES` (`scripts/worlds.ts`), then
   `npm run flyovers -- hero <id>`, give it its slide in the front page's hero
   (`loops/hero-<id>.{mp4,jpg}`); without one the hero simply leaves it out.
5. `deploy/deploy.sh check` (every world in the registry has its data, card, pipeline city and
   docs, this one included), then send its data, `deploy/deploy.sh <id> --data`, **before** the
   merge to main: the push deploys the API (whose seed marks the city `BUILT`), then every
   viewer, and refuses while a world in the registry has no data on the server. Deploying the
   world also tells its city's donors that it is built (once; it needs `ANNOUNCE_HOST` or
   `API_SERVICE`).

The id is `tiny` + a short city code; it is the pipeline's `--city`, the viewer's
`NEXT_PUBLIC_WORLD`, the data folder and the URL path.

## Data contract (pipeline → viewer)

The pipeline writes everything a viewer needs into `tinyworlds-frontend/public/data/<world>/`
(gitignored, reproducible). In production the same folder is served at `/<world>/data/`.

```
data/<world>/
├── manifest.json            # projection, pyramid, tile bitsets
├── tiles/{z}/{tx}_{ty}.webp # lossless WebP, binary alpha (transparent = off the map)
├── overview.webp            # whole map, small: the minimap
├── places.json              # search index
├── hoods.json               # outlines of the city's areas (may be empty)
├── life.json                # ferry routes and flights for the animated layer
├── sights.json              # buildings that light up under the pointer (worlds with sights)
├── sights/<hash>.webp       # each of them drawn on its own, nothing in front of it
├── sights.<locale>.json     # their Wikipedia openings: en-US, pt-BR, es-ES
└── quiz.<locale>.json       # Guess the building's questions (worlds with sights)
```

### Map space and projection

Map space is pixels at native resolution (level 0); x grows right, y grows down. Geodata in the
JSON files stays in lon/lat and the viewer projects it with `manifest.geo`:

```
east  = (lon - lon0) · π/180 · R · cos(lat0)        R = 6371008.8
north = (lat - lat0) · π/180 · R
p = east·sin β + north·cos β        // metres "uptown" (along the grid's main axis)
q = east·cos β − north·sin β        // metres crosstown
X = (p + q) · k
Y = (q − p) · k/2 − h · kz          // h = metres above ground
```

β is the bearing of the city's street grid, so its streets run at exact 2:1 pixel slopes. True
north points `manifest.northDeg` clockwise from screen-up.

### manifest.json

```ts
interface Manifest {
  name: string;                 // the world id: "tinynyc"
  build: string;                // the render's cache-busting id: append as ?v= to tiles, overview
  indexes?: string;             // the indexes' (places, hoods, life, sights, their texts and
                                // pictures): append as ?v= to those; absent: use `build`. A hash
                                // of their contents, written by the pipeline's index and wiki
  tileSize: number;             // 512
  origin: { x: number; y: number };   // map-px position of tile (z, 0, 0)'s top-left, all levels
  levels: {
    z: number;                  // 0 = native; level z is downsampled by 2^z
    cols: number; rows: number;
    tiles: string;              // base64 bitset, row-major, bit (tx + ty·cols), LSB-first: 1 = file exists
  }[];
  bounds: { minX: number; minY: number; maxX: number; maxY: number }; // content bounds, map px
  start: { lon: number; lat: number; scale: number };                 // first view
  maxScale: number;             // deepest zoom, screen px per map px
  northDeg: number;
  geo: { lon0: number; lat0: number; betaDeg: number; k: number; kz: number };
  overview: { src: string; width: number; height: number };           // image spans `bounds`
  attribution: string[];        // shown as they are, in every interface language
}
```

Tile `(z, tx, ty)` covers map px `[origin.x + tx·T·2^z, origin.x + (tx+1)·T·2^z)` horizontally and
likewise vertically (`T = tileSize`). Missing tiles are off the map: the viewer leaves the page
background showing.

### places.json

```ts
type Place = {
  n: string;                    // name
  t: "borough" | "hood" | "landmark" | "park" | "bridge" | "museum" | "station" | "street" | "place";
  lon: number; lat: number;
  b?: string;                   // context line: borough, zone, …
  r: number;                    // rank, higher first on ties
  s?: number;                   // suggested scale when flying there
};
// file: { places: Place[] }
```

`borough` is whatever the city's large divisions are (boroughs in New York; zones and planning
sub-sectors in Ribeirão Preto); the viewer labels the types per world.

### hoods.json

```ts
// file: { hoods: { name: string; borough: string; lon: number; lat: number; rings: number[][] }[] }
// rings: flat [lon0, lat0, lon1, lat1, ...] per ring, simplified
```

### life.json

```ts
// file: {
//   ferries: { name: string; path: number[] }[];   // flat [lon, lat, ...]; a boat sails it there and back
//   flights?: {
//     kind: "helicopter" | "plane";
//     path: number[];      // flat [lon, lat, metresAboveGround, ...]
//     loop: boolean;       // a closed circuit flown forever, or start → end repeated after `pause`
//     speed?: number;      // ground metres per second
//     pause?: number;      // seconds
//   }[];
// }
```

Optional for the viewer: without it the map is simply still.

### sights.json, `sights.<locale>.json`

The structures found in the search (buildings, stadiums, the Statue of Liberty, bridges), each
outlined as the map draws it, and what Wikipedia says of them. Only for a world that has them
(the pipeline's `sights` city field, the viewer's `World.sights`).

```ts
// sights.json: { sights: {
//   id: string;            // "b<seed>", "bridge:<name>", "statue:<i>"
//   n: string; t: PlaceType | "building"; b?: string;   // name, type, context line
//   lon: number; lat: number;                           // where its article is looked up
//   rings: number[][];     // the outline, flat MAP PX rings, even-odd: it includes height, so
//                          // it is screen geometry, not geodata (the one exception to lon/lat)
//   front: number;         // largest ground y of its footprints: the nearer the viewer, the larger
//   anchor: [number, number];  // where its sign hangs (the outline's top), map px
//   sprite?: { src: string; x: number; y: number; w: number; h: number };
//                          // its picture: "sights/<hash>.webp", lossless, transparent but for
//                          // the structure, drawn as the tiles draw it (shadows and all) with
//                          // nothing in front of it; x, y, w, h place it in map px
// }[] }
// sights.<locale>.json: { [id]: { title: string; url: string; text: string; lang: string } }
//   text: the article's opening (≤ 220 characters); lang: the article's own language, "en" where
//   the visitor's has none
```

Optional for the viewer: without them nothing lights up; without a sight's picture it still
lights up, as far as the map shows it.

### quiz.<locale>.json

The questions of "Guess the building", one file per interface language, made by the
pipeline's `quiz` step from `sights.json` and `sights.<locale>.json`: each sight with an article,
its opening with the name blanked out, and three other sights to offer beside it (of the same
kind, nearest first; the same three in every language, so a building's tallies mean the same
thing everywhere).

```ts
// { questions: {
//   id: string;                          // the sight asked about (sights.json)
//   decoys: [string, string, string];    // three other sights' ids: hard's wrong names, any borough or kind
//   sets: {                              // per difficulty it is in ("easy" | "medium" | "hard"),
//     [level]: { all: […3]; area?: […3]; group?: […3]; both?: […3] }   // per scope: wrong names from the
//   };                                   // answer's borough, kind, or both; absent = all's
//   level: 1 | 2 | 3;                    // the easiest difficulty it is in (by its article's page views)
//   group: "buildings" | "museums" | "landmarks" | "stations";
//   area?: string;                       // its borough ("Bronx"), as the data names it
//   parts: string[];                     // the text in pieces; the odd ones (1, 3, …) are blanked.
//                                        // parts.join("") is the text as sights.<locale>.json has it
//   lang: string;                        // the text's own language ("en" where the visitor's has none)
// }[] }
```

Optional for the viewer: a world without it has no game.

## API contract (viewer ↔ API)

GraphQL at `/api/graphql` (same origin in production):

```graphql
enum CityStatus { PROPOSED FUNDED BUILDING BUILT }
type CityMilestone { id: ID! slug: String! name: String! raisedCents: Int! goalCents: Int! donations: Int! benefactorCount: Int! waiting: Int! status: CityStatus! worldId: String }
# waiting: how many people are on the city's list ("Tell me when it is built")
type BenefactorLink { url: String!  title: String!  description: String  icon: String  image: String }
type WallCity { slug: String!  name: String!  worldId: String }
type WallBenefactor { name: String  amountCents: Int!  cities: [WallCity!]!  links: [BenefactorLink!]!  lastGiftAt: DateTime! }
type Query {
  health: String!
  uptime: Int!                                                       # seconds since the API process started
  cityMilestones: [CityMilestone!]!
  cityBenefactors(input: CityBenefactorsInput!): CityBenefactors   # public; null for an unknown or hidden city
  benefactorWall: [WallBenefactor!]!                               # public; everyone who gave to a city, largest first, at most 200
  worldVisits(input: WorldVisitsInput!): [WorldVisits!]!          # public; the worlds asked, in that order
}
input WorldVisitsInput { worlds: [String!]! }                        # 1 to 50 world ids
type WorldVisits { world: String!  visits: Int!  live: Int! }       # live: maps open in the last 75 s
input CityBenefactorsInput { slug: String  world: String }          # one of the two
input CreateDonationCheckoutInput { city: String  amountCents: Int  world: String!  locale: String!  returnUrl: String!  visitId: ID  benefactorName: String }
type DonationCheckout { url: String! }
enum FunnelStep { VISIT DONATE_OPENED CHECKOUT_STARTED CHECKOUT_CANCELLED }
input TrackFunnelStepInput { visitId: ID!  step: FunnelStep!  world: String!  locale: String }
input TrackPresenceInput { visitId: ID!  world: String!  locale: String }
enum QuizLevel { EASY MEDIUM HARD }
input AnswerQuizInput { visitId: ID  world: String!  sightId: String!  choice: String!  choices: [String!]  level: QuizLevel  locale: String }
type QuizPick { choice: String!  count: Int! }
type QuizTally { answers: Int!  picks: [QuizPick!]! }       # picks: most picked first
type Mutation {
  createDonationCheckout(input: CreateDonationCheckoutInput!): DonationCheckout!
  trackFunnelStep(input: TrackFunnelStepInput!): Boolean!
  trackPresence(input: TrackPresenceInput!): Boolean!               # a map, every 30 s while in view
  leaveListWithToken(input: { token: String!, all: Boolean }): Boolean!   # a mail's leave link: no sign-in; true for any token of ours (even used twice, or after the city was built), false for one that is not; all: every list
  answerQuiz(input: AnswerQuizInput!): QuizTally!           # public, 30 a minute per address
}
# donors only (Authorization: Bearer <a donor's session>):
#   query    myGiving: MyGiving!                         # their cities, stones, badges, listing
#   mutation setListing(input: { city: String!, listed: Boolean! }): Boolean!
#   mutation setDisplayName(input: { name: String! }): String!   # answers the cleaned name
#   query    myLinks: MyLinks!                           # their links (each with its id), max, givenCents, picturesFromCents, hidden
#   mutation addLink(input: { url: String! }): MyLink!   # reads the page; refreshLink(input: { id }) reads it again
#   mutation removeLink(input: { id: ID! }): Boolean!
#   query    myLists: MyLists!                           # { cities: [{ slug, name, status, raisedCents, goalCents, waiting }], donated: [slug], newCities: Boolean }; donated: unbuilt cities they gave to (told without a list)
#   mutation joinList(input: { city?: String, locale?: String }): MyLists!   # city omitted: "new cities"; once; a city that is built or unknown is not joined
#   mutation leaveList(input: { city?: String }): MyLists!
# admins only (Authorization: Bearer <an admin's session>):
#   me, donationFunnel
#   query    benefactorNames: [BenefactorName!]!         # newest listed gift first, at most 100; each with its links
#   mutation setNameHidden(input: { donorId: ID!, hidden: Boolean! }): Boolean!
#   mutation setLinksHidden(input: { donorId: ID!, hidden: Boolean! }): Boolean!
#   query    listCounts: ListCounts!                     # { cities: [{ name, slug, waiting }] most first, newCities: Int }: counts only, never an address
```

`amountCents` (100 to 1,000,000) fixes the amount; without it the donor chooses on Stripe's page
(from US$1). `visitId` is the tab's visit (a UUID from session storage); `world` is a world's id
or `"home"`. In `answerQuiz`, `sightId` is the building asked about and `choice` the sight id
picked (right when they are equal); a visit's answer to a building is kept once, and without
`visitId` none is kept but the tally is still answered. `choices` are the names the page offered
(up to four, the building and the pick among them): `picks` then counts only those, else the 20
most picked; `answers` is everyone who answered the building. `level` is the game's difficulty
(each offers other wrong answers): answers are kept and tallied per level, `HARD` when absent. `benefactorName` (1 to 40 characters, cleaned by the API) asks to be named on the
city's benefactors for this gift; without it the gift is counted and not listed. A founder's
and a benefactor's row of `cityBenefactors` carries `links: [BenefactorLink!]!` too (none on an
unnamed row). `benefactorCount`, on a milestone and on `cityBenefactors`, is how many people
gave to the city in dollars: a donor once, however many gifts, and a gift that came without an
address as one; `donations` counts the gifts. A link's `icon` and `image` are paths on the API's own host
(`/api/link-images/<id>`, WebP, kept for good by a browser); `image` is null on the public
lists until the donor has given US$10 in all. REST: `GET /api/link-images/<id>`, `GET /api/sight-pictures/<world>/<file>` (a lit building's picture as a PNG, for the mails), `POST /api/lists/unsubscribe?t=<token>` (a mail client's one-click leave, RFC 8058), `POST /api/stripe/webhook`, and signing in, for admins and donors alike:
`POST /api/auth/magic-link { email, returnUrl, locale?, purpose?, list? }` (always `202`; `list` is a city's slug, or `*` for "new cities", on donor links only: the list is joined when the link or code is used, server side, so a link opened on another device still joins; a list that cannot be joined is dropped silently), then
`POST /api/auth/verify` with `{ token }` or `{ email, code, purpose? }`, answered
`{ accessToken, expiresAt, admin | donor: { id, email } }`. `purpose` is `"admin"` (the default)
or `"donor"`; a session of one kind is `FORBIDDEN` on the other's queries. When the contract
grows, deploy the API before the viewers: an older API refuses a checkout that carries a field
it does not know, and the site then falls back to its payment link. Details in
`tinyworlds-api/CLAUDE.md`.

## Running and deploying

- `./dev.sh [world]` opens tmux with the viewer's dev server, the API and a pipeline shell.
- The pipeline is run by hand (`npm run all -- --city <id>` in `tinyworlds-pipeline`).
- **A push to `main` deploys itself** (`.github/workflows/deploy.yml` runs `deploy/deploy.sh
  release`): the API, through its host's deploy webhook, when `tinyworlds-api/` changed, waiting
  until the new one answers; then every viewer and the front page, without map data, when
  `tinyworlds-frontend/` or `deploy/` changed. The server keeps which commit each part came from
  (`deployed/api`, `deployed/viewers`), so a failed or skipped run is made up by the next one
  (or the daily one). Nothing of where it goes is in the workflow: it reads the repository's
  `production` environment secrets.
- By hand: map data, which is not in git (`deploy/deploy.sh <world> --data`, or `--index` for
  the indexes); `deploy/deploy.sh <world | home>` builds a viewer and rsyncs it (and the
  world's data) to the web server; `deploy/deploy.sh all [--parallel[=N] | --serial]
  [--no-data]` checks and builds every world in the viewer's registry and the front page, and
  uploads only if all of them built. A build from a tree that lacks what the server runs is
  refused. Uploads use rsync alone, with a key that can do nothing else. After uploading a world
  it runs the API's announce command in the API's container (through `ANNOUNCE_HOST`, a key
  that may run only that, or a shell and `API_SERVICE`), which mails a newly built city's
  donors once. The API is a container built from `tinyworlds-api/Dockerfile`. See
  `deploy/README.md`.

## Conventions

- npm, Node 22, TypeScript strict, ESLint + Prettier in every sub-project.
- Raw downloads and generated tiles are never committed (`tinyworlds-pipeline/data/`,
  `tinyworlds-frontend/public/data/`). The share cards in `tinyworlds-frontend/public/og/`, the
  mails' pictures in `tinyworlds-frontend/public/email/` (`npm run email-images` makes them) and
  the front page's loops in `tinyworlds-frontend/public/loops/` are, and so is each film's music
  bed (`tinyworlds-videos/*/assets/music/`: a film is timed to it); the videos' plates, takes,
  sound effects and renders are not.
- Every picture of a map, still or moving, is cut from the real tiles or filmed from the real
  viewer (`tinyworlds-videos`): nothing is redrawn for a card, a loop or a film.
- Attribution is part of the product: the About panel credits each world's data sources
  (`manifest.attribution`).
- No hard-coded interface strings in the viewer: everything goes through its i18n dictionaries
  in the three languages.
